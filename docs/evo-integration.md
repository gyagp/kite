# Evo in Kite

**Current UI:** model conversion and authoring screens have been removed at the
user's request. The Model Lab entry points described below document the initial
integration; the underlying developer tools and saved evidence remain available.

**Updated:** the asset/environment relocation is complete. Kite no longer requires the original Evo directory. See [standalone migration and performance](standalone.md) for the current layout, image output folder, and selected optimizations. The reference-in-place details below describe the initial integration.

Kite 0.2 includes Evo's implementation, authoring tools, tests, recipes,
benchmarks, requirements and documentation. The Python package is now `kite/evo/`;
Kite's embedding adapter imports this package instead of `evo/src/evo`.
`evo_resources/migration.json` records the source-file hashes for all 100 imported
files. The source directory had no Git metadata, so there is no invented revision.
The original Evo directory was not modified.

| Qwen-Image text-to-image and reference-image editing | Image Studio |

All 21 non-server commands have generated forms, full argument access, command
help, live logs, saved artifacts, cancellation and retained run history. `ui`,
the 22nd command, remains available as the original compatibility workbench:
`python -m evo ui`. Its features are also accessible in Kite's integrated tabs.
The original Python API (`import evo; evo.build(...)`) and CLI remain available.

Optional exporters still need their upstream dependencies and supported model
architectures. A successful conversion does not establish inference accuracy or
performance. The migration does not turn Evo's documented research proposals
or unimplemented adapters into working features.

## Existing data and environments

Model weights, runtime DLLs, processor dependencies and Python environments stay
at their current paths, including `E:/workspace/project/evo`. They are referenced
in place, not duplicated. This is a code/capability integration, not a copy of
hundreds of GB of model data. To retire the old directory, first relocate those
assets and update Settings and Image Studio → Runtime.

On first use, Model Lab copies `models.json`, `performance.json` and
`wishlist.json` from Evo's workbench into Kite's application-data `workbench/`.
Subsequent edits affect Kite's copies. Benchmark evidence remains read from its
original files, preserving source paths and numerical provenance. On the current
machine this exposes 66 observations. Missing/invalid evidence remains subject
to Evo's existing filtering rules.

Tool outputs live in `<Kite data>/lab-jobs/<job id>/`. Use `{output}` in an output
argument for a fresh path; nested report parents are created automatically.
Included recipes are copied into the job and their local input paths resolved
against the original asset root, while output points into the new job. User
recipes retain their own path semantics. Completed compatible packages at the
job's output path are imported into My models automatically. Arbitrary ONNX/GGUF
files can be added to Graph library.

Image CLI tools default to Image Studio's Python, dependency folders and image
DLL. Image generation defaults to Vulkan, short-blocks and FP32 accumulation.
Explicit CLI backend/variant options remain available. Embedding CLI tools receive
the local processor directory unless explicitly overridden. The HTTP host can
still use standard-library-only Python: graph evidence falls back to the selected
authoring Python when ONNX is not installed in the host.

## Qwen-Image Studio

Four included presets were generated by the actual local Qwen-Image model:

- **A city that forgot gravity** — a glass sphere, cloud city and red kite.
- **Let imagination take flight** — a bilingual KITE / 想象起飞 poster.
- **Objects from tomorrow** — cobalt glass and metal product photography.
- **From a line to a world** — the official boat sketch becomes a yacht photo,
  with a draggable before/after divider.

The bundled previews are labeled as model output. Selecting a preset fills its
prompt, seed, canvas and reference input. Generate/Transform runs inference again;
it never substitutes a bundled preview for an inference result. Up to three
uploaded reference images are supported. These four tests include one reference
image, not a qualification of every possible multi-reference combination.

Images, prompts, seeds, settings and timing metadata persist in Your gallery.
Each generation is an eight-step, CFG-1 diffusion run. Square 512, 768 and 1024,
plus 768×1024 and 1024×768 canvases are offered. Runtime configuration is separate
from chat/embedding so the image DLL does not replace their selected provider.

The **denoiser and prefix graphs run native ORT WebGPU / Vulkan** with the
source-built BK64 floating-zero-point provider. **Text/reference encoding and
RGBA VAE decoding run local PyTorch / CUDA**. CUDA Torch is therefore required
for this complete pipeline. This release does not claim a fully ONNX pipeline.

FP16 accumulation produced a non-finite prediction at step 8 of the new 768×768
sky-garden workload. Studio uses FP32 MatMul accumulation for both prefix and
denoising on Vulkan, extending Evo's documented edit workaround. All four demos
completed with this setting. Sky-garden's final latent is exactly equal with
capture on/off (maximum absolute difference 0). This is a workload-specific
check, not a universal runtime correctness claim.

Performance cards show wall time for text/reference encoding, prefix, denoising
and VAE decode, plus prefix/denoiser execution time and individual denoising
steps. Phase totals include process startup, model loading, shader compilation
and readbacks. The four original cold runs took approximately 47–62 seconds end
to end on this RTX 5080. These are interactive observations, not warmed benchmark
comparisons. Evo's previous matched report still shows ONNX slower than the GGUF
baseline; the UI does not claim a speed win.

Image phases use separate supervised processes to release CUDA/WebGPU memory
between them. All image, chat, embedding and tool jobs share one queue; Stop
terminates the active process tree. Successful image runs remove generated
prefix/fixture/latent scratch files and retain PNG, logs, request and metrics.
Failed runs keep diagnostic scratch files under their own image job directory.
